# Database review

Reviewed on 2026-10-06 against the production D1 schema, Worker queries, import/revocation tools, and retention jobs. All 14 application tables and 106 columns were inspected. This is a review, not an applied migration.

The main simplification opportunities are legacy account roles, duplicated photo keys, unused format totals, and the separation between removal cases and reports. Login, email delivery, download follow-up, and restoration still need persistent records even without an organiser dashboard.

## Recommended cleanup

| Change                                                      | Reason                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Remove `accounts.role`                                      | The Worker reads it but never uses it to authorise anything. Restoration is authorised by Cloudflare Access.                                                                                                                                                                                                                                           |
| Remove `photos.thumbnail_key`, `preview_key`, `full_key`    | Imports populate them, but serving reads `photo_variants.object_key`. Two copies can drift.                                                                                                                                                                                                                                                            |
| Remove `removal_cases.cross_channel_reviewed`               | Always inserted as zero; no current code reads or changes it. It belongs to the retired organiser workflow.                                                                                                                                                                                                                                            |
| Remove `daily_aggregates.full_downloads`, `quick_downloads` | They are maintained but never read by the current interface or operating tools. The retained individual download records already identify the format when needed for rights follow-up. Keep the aggregate `downloads` total.                                                                                                                           |
| Remove `code_challenges.email`, `language`                  | These are written but never read back. The email outbox already contains the recipient and rendered message; verification uses the email hash.                                                                                                                                                                                                         |
| Consider merging `removal_cases` and `removal_reports`      | Every new request currently creates its own case and report; requests are not grouped into shared cases. One removal-request table could retain the current fields needed for retries, restoration, and audit without duplicating requester, explanation, status, version, and timestamps. This requires a deliberate migration and concurrency tests. |
| Remove redundant indexes                                    | `accounts_email_hash_idx` duplicates the unique constraint on `email_hash`. `download_request_binding_idx` adds no uniqueness beyond the primary key on `request_id`.                                                                                                                                                                                  |

The indexes on `photos.moderation_operation_id` and `removal_cases.moderation_operation_id` are candidates for removal: current queries find rows by primary key before checking the operation token. Keep the token columns themselves; they prevent one restoration from completing another restoration's audit steps. Review query plans before removing other indexes.

## Table and column coverage

| Table                 | Columns and assessment                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `accounts`            | Keep `id`, `email`, `email_hash`, `active`: eligibility, login, and contacting downloaders. `created_at` and `revoked_at` are useful operating history. Remove unused `role`.                                                                                                                                                                                                                                                              |
| `code_challenges`     | Keep `id`, `account_id`, `email_hash`, `code_hash`, `created_at`, `expires_at`, `resend_after`, `attempts`, `consumed_at`, `request_ip_hash`: verification, expiry, single use, and abuse limits. Remove redundant `email` and `language`.                                                                                                                                                                                                 |
| `sessions`            | Keep `token_hash`, `account_id`, `csrf_hash`, `expires_at`, `licence_version`, `revoked_at`: authentication, CSRF protection, current terms acknowledgement, and revocation. `created_at` is useful session history.                                                                                                                                                                                                                       |
| `photos`              | Keep `id`, `category`, `filename`, `version`, `status`, `width`, `height`, `moderation_operation_id`. The filename remains useful for downloads, ordering, and removal emails even though the interface hides it. `created_at` and `updated_at` record import/publication changes. Remove the three duplicated object-key columns.                                                                                                         |
| `photo_variants`      | Keep all: `photo_id`, `format`, `object_key`, `width`, `height`, `bytes`, `sha256`, `content_type`. They select the R2 object and provide image dimensions, download sizes, validation hashes, and response metadata.                                                                                                                                                                                                                      |
| `licence_versions`    | Keep `version`, `current`, `created_at` to select the active terms. `en_json` and `fr_json` are not read by the application, which renders the checked-in terms, but are useful historical copies of acknowledged terms. Preserve them as immutable snapshots or replace them with another explicit version archive.                                                                                                                       |
| `removal_cases`       | Currently used: `id`, `photo_id`, `status`, `created_at`, `updated_at`, `moderation_operation_id`. `requester_account_id` and `explanation` duplicate the report and are not read from this table. `photo_version` is recorded but not consulted during restoration, which checks the current photo version and link version. `cross_channel_reviewed` is unused. Merge with reports or remove duplication if separate cases are retained. |
| `removal_reports`     | Keep `id`, `case_id` while cases remain separate, `photo_id`, `requester_account_id`, `explanation`, `request_id`, `status`, `created_at`, `resolved_at`: removal trigger, retry binding, quota checks, notification content, blockers, and retention. `photo_version` records the version involved, although no current query uses it to authorise restoration.                                                                           |
| `notification_outbox` | Keep all: `id`, `kind`, `payload_json`, `attempts`, `available_at`, `locked_until`, `sent_at`, `last_error`, `created_at`. These implement delivery retries and prevent concurrent senders from claiming the same message. Successful delivery clears the payload.                                                                                                                                                                         |
| `moderation_audit`    | Keep all: `id`, `actor_account_id`, `action`, `case_id`, `photo_id`, `reason`, `expected_version`, `created_at`. They record restoration identity and outcome. The actor is a Cloudflare Access subject, not an attendee account; renaming the column to `actor_subject` would clarify this without changing behaviour.                                                                                                                    |
| `daily_aggregates`    | Keep `day`, `photo_id`, `opens`, `downloads` for the visible activity counts. Remove unused `full_downloads` and `quick_downloads`.                                                                                                                                                                                                                                                                                                        |
| `album_visits`        | `day` and `visits` are written but not read by the current application. Remove the table and its event input if album-visit analytics are no longer wanted; it is not required for per-photo view/download counts.                                                                                                                                                                                                                         |
| `viewer_opens`        | Keep `photo_id`, `session_key`, `opened_at` for counting a photo once per session and expiring deduplication records. This is a temporary pseudonymous deduplication ledger, not an aggregate table. The session-derived key permits linking opens within a session; photo-scoped keys would reduce that linkability if retained.                                                                                                          |
| `download_requests`   | Keep all: `request_id`, `account_id`, `photo_id`, `photo_version`, `format`, `created_at`. They prevent duplicate counting on retries and let an operator find the recipients of a specific photo for rights follow-up. Records expire after 90 days.                                                                                                                                                                                      |

`_cf_KV` and `d1_migrations` are Cloudflare/migration bookkeeping; leave them alone. Primary keys, foreign keys, and the quarantine trigger are functional safeguards, not optional reporting fields.

## Other findings

- Per-photo counts currently display the last 90 days, although the aggregate rows are retained longer. Decide whether the interface should display lifetime totals or explicitly label the window; individual download-record retention need not limit anonymous totals.
- The licence seeder can overwrite the text for an existing version. Historical version text should be immutable if it is kept as evidence of the terms acknowledged.
- Eligibility imports are additive and do not record source provenance in D1. Keep the reviewed source manifest privately and reconcile its union before revoking an address. Do not copy registration profiles or other CSV personal data into the application database.

## Live checks

The production schema matches the five checked-in migrations. There are 358 published photos, 1,432 variants, no incomplete variant sets, no foreign-key violations, and no inconsistencies between the aggregate download total and its stored format totals. Empty removal/audit tables are expected before the first live removal; emptiness is not a reason to drop that workflow.

A cleanup should use a new migration, update import tools alongside Worker queries, preserve existing moderation/download records, and rerun authentication, removal/restoration race, retry, and retention tests. Do not rewrite migrations already applied to production.
